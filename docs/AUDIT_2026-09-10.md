# Zenith Fitness — in-depth audit, 2026-09-10

Scope: every reachable screen at 412×915 in both themes, as a gym member and
as a gym owner; the whole `src/` tree statically; the deployed Firestore rules
against the live data; the production bundle.

Baseline before any change: `eslint` clean, 291/291 tests pass, `tsc` clean,
build clean. **Zero JavaScript errors were produced on any of the 42 screen
visits** (28 member × 2 themes, 14 owner) — the app is in good shape. What
follows is what was wrong underneath that, and what is worth doing next.

Method notes are at the bottom; the scripts live in the session scratchpad.

---

## 1. Fixed in 3.25.0

### 1.1 "0 followers" with five buddies — root cause, not a retry

`syncBuddyFollows` ran on the device at **22:09 on 2026-09-09**. The Firestore
rule that lets one side write the *reciprocal* follow edge was deployed at
**23:10** — an hour later. So every "X follows me" half was rejected, and
because the failures were swallowed by `.catch(() => {})`, the function then
wrote its "done" timestamp and the 24-hour guard blocked any retry.

Live data confirmed it exactly: 8 buddy pairs, 5 follow edges, all of them
outgoing from one uid.

Three things changed:

- `followBuddy` no longer swallows either half. A failure propagates.
- `syncBuddyFollows` records the run **only if it completed**, and finishes by
  recounting `followerCount` / `followingCount` from the edges themselves
  rather than trusting increments that may never have landed. Your own profile
  is the one document the rules let you set outright, so the recount is
  authoritative and self-healing from here on.
- The guard key carries a schema version (`..._sync2_`), so this fix re-runs
  once on every device instead of waiting out the stale 24-hour window.

Production data was repaired directly: **11 missing edges written, 8 profiles
recounted**. Your profile now reads 5 followers / 5 following.

### 1.2 In-app notifications

Before: a flat grey card faded in below the app bar, sat for 5 s, and left. A
buddy request was not even tappable — the only way to answer one was to walk
to the Buddies screen and find it.

Now:

- It drops in **over** the app bar with a small overshoot (`notif-in`,
  460 ms, `cubic-bezier(.22, 1.15, .36, 1)`), wears the sender's actual
  avatar with a solid coloured type chip, and **draws its own dwell timer** as
  a bar that drains under the card.
- **Buddy requests carry Accept / Not now inside the card.** `requestId` and
  the sender's photo now ride on the notification document so the card can act
  without a lookup. Accepting plays the PR cue and the card reports "You are
  buddies now" before it leaves.
- A new `notify` sound + haptic cue fires on arrival (E5 → C6, two beats).
- Requests and session invites stay **unread** until answered and dwell for
  12 s instead of 5; everything else 6–6.5 s.
- Swipe up or tap the cross to dismiss. Up to three stack, newest on top.
- The header count badge now pulses (`notif-ping`) while something is waiting.
- Everything respects `prefers-reduced-motion`.

Verified end to end against production: owner sends a request through the UI →
member's card appears with Accept → tapping Accept creates the buddy pair,
**both** follow edges and 1/1 counters on both sides, with zero console errors.

### 1.3 Bundle: a version bump was re-downloading 1.07 MB

`manualChunks` only split React, so Firebase (456 kB) and lucide (41 kB) were
baked into the app chunk and re-downloaded on **every** release.

    before   index.js 1,067 kB  (331 kB gzip)
    after    index.js   592 kB  (186 kB gzip)
             vendor-firebase 456 kB — cached across releases
             vendor-icons     41 kB — cached across releases

A repeat visitor after a version bump now pulls ~45 % less. On the gym's
network that is the difference between the splash screen and a stall.

### 1.4 Nested `<button>` on the Home buddies row

`ListRow` renders a `<button>` when it has an `onClick`, and `HomeTabView`
passed another `<button>` (the avatar → profile) as its `leading`. Invalid
HTML; React warns; the inner tap is unreliable on some Android WebViews. Only
visible once you actually have a buddy, which is why it survived this long.
Replaced with a `role="button"` span that handles Enter/Space.

### 1.5 Profile heatmap opened six months in the past

26 weeks is wider than a 412 px phone and the newest column is the rightmost
one, so the heatmap opened on March and today was off-screen. It now opens on
this week, with the day-of-week letters **pinned** so they survive the scroll.

### 1.6 Smaller things

- "Change day" wrapped onto two lines on the home card — it now holds one line
  and the reason text truncates instead.
- **48 icon-only buttons** had no accessible name (back, close, add, …). All
  labelled. Three were skipped deliberately: their text lives in a JSX
  expression, so a label would have shadowed the visible words.
- Tap targets: the follower/following counts were 18 px tall and the app-banner
  dismiss was 20×20. Both padded out without moving anything visually.
- Two `console.log` calls that were reporting genuine failures (`StatusBar
  setup error`, `backButton listener failed`) now log at `warn` / `error`.

## 2. Found, deliberately not shipped tonight

### 2.1 Anyone can force a buddy relationship (security)

`firestore.rules`:

    match /buddies/{pairId} {
      allow create: if signedIn() && request.auth.uid in request.resource.data.users;
    }

Nothing checks that the other person agreed. A signed-in user with the SDK can
write `buddies/<sorted pair>` with `users: [me, anyone]` and become their
buddy — which then also opens `chats/chat_<pair>` (same shape of rule) and,
since 3.24, entitles them to write the reciprocal follow edge.

The app's UI never does this, so the practical risk is low, but the rule is
wrong.

**Phase 1 shipped now:** `acceptBuddyRequest` writes the originating
`requestId` onto the buddy document — the recipient's proof of consent.

**Phase 2 — landed in 3.26.0 (Rishi's call on 2026-09-12: flip now, older installs must update):** rules cannot be tightened the
same day, because they apply to every client instantly and the APKs already on
people's phones do not write `requestId`. Once 3.25 is out in the field:

    function buddyPairId(a, b) { return a < b ? a + '_' + b : b + '_' + a; }
    function consented(reqId) {
      return reqId is string
        && exists(/databases/$(database)/documents/buddyRequests/$(reqId))
        && get(/databases/$(database)/documents/buddyRequests/$(reqId)).data.toUid == request.auth.uid;
    }
    match /buddies/{pairId} {
      allow create: if signedIn()
        && request.resource.data.users.size() == 2
        && pairId == buddyPairId(request.resource.data.users[0], request.resource.data.users[1])
        && request.auth.uid in request.resource.data.users
        && consented(request.resource.data.requestId);
      …
    }

And the matching one for chats, which can use `existsAfter` because the buddy
doc is written in the same batch:

    allow create: if signedIn() && request.auth.uid in request.resource.data.users
      && chatId == 'chat_' + buddyPairId(request.resource.data.users[0], request.resource.data.users[1])
      && existsAfter(/databases/$(database)/documents/buddies/$(buddyPairId(…)));

Verify both with the `buddy_e2e.mjs` flow before and after deploying.

### 2.3 Every pushed screen carries an empty app bar

`AppShell` renders the `AppBar` with no title on every non-tab view, because
those views draw their own back-arrow + title inline. The result is ~66 px of
empty chrome above the real header — visible on Members, History, Settings,
every gym sub-screen. On a 915 px phone that is 7 % of the viewport, on every
screen except five.

Two ways out: hide the bar entirely on pushed views (the streak pill and
buddies icon then live only on tab roots, which is arguably where they belong),
or move the pushed view's title into it and delete the inline headers. Both are
a global navigation change touching ~25 screens, which is your call rather than
mine — hence not done. It is the single biggest visual win available.

### 2.4 Dead code

`getBuddyWorkouts` / `getBuddyStats` in `src/buddyService.ts` have no callers,
and they could not work if they did: they read `users/{buddyUid}/data/workouts`,
which the rules restrict to the owner. Anything that wants a buddy's numbers
needs a mirrored public document. Flagging rather than deleting.

## 3. Where the product goes next

Measured against the competitor work in `../zenith-audit-2026-09-07/PRODUCT_RESEARCH.md`,
these are the gaps that remain, ranked by what they do for the gym pitch.

1. **Progressive-overload suggestions in the active workout.** Still the single
   most-cited "why I pay" feature in Fitbod/Jefit reviews, still not built, and
   still deterministic and free: last session's weight × reps is already
   stored; suggest +2.5 kg or +1 rep when every set hit, hold when RPE ≥ 9.
2. **Renewal automation for owners.** The expiring list exists; the WhatsApp
   deep link and the `upi://` payment link do not. The research is unambiguous
   that renewal is where independent gyms lose money, and this costs nothing
   to run.
3. **Monthly gym challenge + leaderboard.** Everything it needs (check-ins,
   workouts, dailyStats) is already collected. This is the thing that makes the
   feed worth opening twice a week.
4. **A readiness number from Health Connect.** Sleep + resting HR + recent load
   → one morning figure. Zen can already explain it; the data is already synced.
5. **Adaptive weekly targets check-in** (the MacroFactor loop). The phase engine
   already computes adaptive maintenance — surface it as a weekly card that
   proposes the new numbers with one tap to accept.
6. **Notification centre.** Now that arrival is handled well, the Alerts tab is
   the weak half: it is a flat list with no grouping, no "mark all read" from
   the header, and no empty-state guidance.

## Method

- Static: TODO/FIXME markers (0), `: any` / `as any` / `@ts-ignore` (0 real —
  4 matches were the word "any" in prose), `console.log` (6, 4 legitimate),
  unbounded Firestore reads (none — every list query is capped or
  per-user-bounded), `<img>` without `alt` (none), icon-only buttons without an
  accessible name (51 found, 48 fixed).
- Runtime: puppeteer at 412×915 DPR 2, signed in through the DEV `?__devEmail`
  hook as the seeded QA member and owner. Each screen was audited in-page for
  document-level horizontal overflow, elements protruding past the viewport,
  text clipped without an ellipsis, and tap targets under 36 px, and screenshot
  in both themes. Console errors, page errors and dialogs were collected
  throughout.
- Data: read production Firestore with firebase-admin (`follow_probe.mjs`),
  and compared the deployed ruleset against `firestore.rules` via the
  Firebase Rules API — they are identical.
